# Korean Sunrise — Аналитические заметки и дорожная карта боевого исполнения

## 1. Телеметрия сигналов и отсев токсичных монет

Для базового отсева монет данные уже собираются:
- `drain_ratio`, `dev_z`, `net_exec_edge_bps`, `follower_spread_bps`, `follower_top3_ask_usd`
- Итоговый `net_pnl_bps` и траектория `path` в виде `[dt, up_mid_move, f_mid_move, f_exec_pnl, rem_edge]`
- Долларовая фактура пробоя на Upbit (`leader_norm_depth_usd`, `leader_swept_usd`, `pair_sigma_bps`)
- Имбалансы стаканов лидера и фолловера (`leader_imbalance`, `follower_imbalance`)
- Лаги и возраст котировок (`upbit_latency_ms`, `follower_book_age_ms`)
- Пиковый профит, просадка и тайминг пика (`max_exec_pnl_bps`, `min_exec_pnl_bps`, `time_to_peak_sec`)
- 5-мерный path для точного построения кривой маркаута (markout curve на 100 мс, 250 мс, 500 мс, 1 с, 2 с, 5 с)

## 2. Архитектура боевого автомата (Execution & Risk)

Разворачивать боевых торговых ботов на этой основе требует следующих компонентов:

### 1. Модуль ордер-менеджмента (Order Execution Manager)
- **Рыночный вход (Market Entry)**: По сигналу `SunriseSignal` бот мгновенно отправляет маркет-ордер на покупку на фолловере на рассчитанный объем `suggested_size_usd`.
- **Управление позицией**: Обработка заполнения (fill), отслеживание реальной цены входа, выставление защитного стоп-лосса и выход при `converged`, `reversed` или `timeout`.

### 2. Учет балансов и риск-менеджмент (Risk Management & Inventory)
- Контроль свободной маржи на фьючерсных аккаунтах.
- Ограничение максимальной экспозиции на одну монету.
- Защита от проскальзывания (Slippage Protection): если спред резко расширился, блокировать вход.

### 3. Режим «Dry Run / Paper Trading»
- Эмуляция исполнения по реальному `best_ask` в момент сигнала.
- Расчет честного PnL по ходу движения стакана фолловера.
- Проверка Realized PnL с учетом реальных проскальзываний на потоке данных.

## 3. Синхронизация времени на VPS (Chrony NTP) и часовые пояса Bithumb

В арбитраже корейского лид-лага физический лаг между Сеулом (Upbit / Bithumb) и Токио (Binance / Bybit / OKX) составляет всего 28–32 мс, а внутри Сеула — 0.5–2.0 мс.
Поэтому критически важно, чтобы часы сервера шли синхронно с мировым эталоном времени (рассинхронизация < 0.5 мс).

1. **Обязательная установка Chrony на боевом Linux VPS:**
   ```bash
   sudo apt update && sudo apt install -y chrony
   sudo systemctl enable --now chrony
   chronyc tracking
   ```
2. **Парсинг таймзон Bithumb:**
   - Стаканы Bithumb передают Unix-эпоху в микросекундах (`datetime="1792542995509097"`).
   - Сделки Bithumb передают наивную дату в корейском времени `KST (UTC+9)` (`contDtm="2026-10-21 09:37:26.883114"`).
   - Функция `normalize_exchange_ts` в `models.py` принудительно задаёт `tzinfo=UTC+9` и приводит дату к POSIX UTC Epoch, благодаря чему метрика сетевой задержки `leader_latency_ms` работает корректно на любой машине.

## 4. Двойные ловушки микроструктуры: Bithumb-Exclusive и Пылевые подтверждения

### 1. Токсичность Bithumb-Exclusive ($N=99$)
* **Эффект:** Монеты, которых нет на Upbit, имеют в 3–5 раз меньшую глубину стакана на корейском рынке.
* **Следствие:** Порог `BITHUMB_MIN_SWEPT_USD = 3000.0` пробивается единичными розничными сделками. Возникает спред-блокаут, который не поддерживается институциональным потоком. На перпах CEX происходит моментальный токсичный откат.
* **Решение:** В ежедневном отчёте анализируем Net PnL когорты `Bithumb Solo`. При отрицательном матожидании поднимаем порог `BITHUMB_MIN_SWEPT_USD` до $5,000–$10,000.

### 2. Защита от пылевых подтверждений (Dust Confirmation Guard)
* **Эффект:** В режиме телеметрии `recent_other_buys > 0.0` подтверждает сигнал даже при сделке на $2–$5.
* **Следствие:** В реальной боевой торговле (`REQUIRE_KOREAN_CONFIRMATION=true`) институциональный снос на Upbit ($50k) может быть ошибочно "подтвержден" случайной мелкой транзакцией на Bithumb.
* **Решение:** В боевом режиме устанавливать `MIN_KOREAN_CONFIRM_USD=500.0` (или $1,000.0), чтобы подтверждение требовало реального объема.
